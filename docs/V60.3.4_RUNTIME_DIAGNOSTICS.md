# V60.3.4 — Runtime diagnostics for shared API/D1 failures

## Why this patch exists
The supplied Android screenshots show several unrelated pages failing together: public catalog counters are zero, Share returns `SERVER_ERROR`, Admin analytics fails, and tenant Admin login cannot complete. That pattern points first to a shared Worker/D1 runtime path, not to independent CSS defects.

## Code changes
- `/api/health` now performs a real `SELECT 1` against the configured D1 binding. The old health response only checked whether `env.DB` was truthy, which did not prove the database was reachable.
- Health reports the presence of core tables (`products`, `tags`, `settings`, `tenant_accounts`, `tenant_products`, `tenant_sessions`, `admin_sessions`) without returning user rows or secrets.
- Unhandled Worker errors now write a structured `[worker-request-error]` log containing request ID, HTTP method, route, exception name/message, and a bounded stack excerpt. The public response returns only a request ID and a generic message.

## What this does NOT do
- It does not create/replace the production D1 database, change its ID, reset data, or repair Cloudflare dashboard bindings.
- It does not migrate production data automatically or change payment/auth business logic.
- It cannot prove that the live production Worker has this code until the archive is deployed.

## Required production verification
1. Deploy the `cloudflare/` Worker using the included `wrangler.toml`; keep the existing `DB` binding and all secrets/vars intact.
2. Open `https://teostudio.top/api/health`.
3. Check `database.binding`, `database.queryOk`, and `database.requiredTables`.
4. If `queryOk=false`, inspect Cloudflare Worker logs for `[health] D1 probe failed` and verify the production binding named `DB` points to the existing `teo-studio` D1 database. Do not create a new database or reset the current one.
5. If `queryOk=true` but a route still returns `SERVER_ERROR`, use its `requestId` to find `[worker-request-error]` in Cloudflare Logs and fix the exact failing query/schema from that stack.
